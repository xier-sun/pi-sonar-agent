# DingTalk 确认卡片模板设计

## 1. 目标

这张卡片用于承接 `pi-sonar-agent` 的钉钉手动触发闭环，目标是：

- 让触发人快速确认“这次到底要修什么”
- 让配置项一眼可读，避免误把旧任务参数带到新任务
- 让“确认执行 / 取消”这两个动作语义清晰、可回调
- 在没有卡片权限或卡片模板未配置时，仍然可以平滑回退到文本确认

这张卡片**不是审批卡**，也不应该复用“报销 / 同意 / 驳回”之类的审批模板语义。

## 2. 使用前提

要启用正式确认卡片，需要同时满足：

1. 当前钉钉应用已开通权限：`Card.Instance.Write`
2. 已在钉钉卡片平台创建专用模板
3. 将模板 ID 写入项目 `.env`

```env
DINGTALK_CONFIRMATION_CARD_TEMPLATE_ID=<your-template-id>
```

如果以上任一条件不满足，当前项目应继续使用：

- 文本待确认消息
- `确认任务 <job_id>`
- `取消任务 <job_id>`

## 3. 卡片定位

这张卡片的定位是：

- **任务确认卡**
- 面向**触发人**
- 用于在执行前确认本次运行配置

不承担这些职责：

- 不直接展示修复结果
- 不承担审批流状态机
- 不承担历史任务查询
- 不承担复杂表单输入

## 4. 卡片展示结构

建议卡片采用 4 个区块：

1. 头部状态区
2. 本次任务摘要区
3. 本次运行参数区
4. 操作按钮区

### 4.1 头部状态区

建议展示：

- 标题：`确认执行 Sonar 自动修复`
- 状态标签：`待确认`
- 副标题：`请确认本次修复配置后再执行`

### 4.2 本次任务摘要区

建议展示这些核心字段：

- 任务编号
- 仓库
- 作者
- 项目
- 基线分支
- 触发人

这部分是 reviewer 和触发人最先确认的“身份信息”，必须置顶。

### 4.3 本次运行参数区

建议展示这些字段：

- `issue_keys`
- `skip_issue_keys`
- `max_issues`
- 审阅者账号
- 结果通知账号

建议规则：

- 未指定时明确显示：`(未指定)`
- 过长列表要换行，不要挤成一行
- 如果是“更新已有待确认任务”，可以额外显示：
  - `本次补充/修改: ...`

### 4.4 操作按钮区

固定两个按钮：

- `确认执行`
- `取消`

按钮行为：

- `确认执行` -> `confirm_fix_job`
- `取消` -> `cancel_fix_job`

按钮文案不要写成：

- `同意`
- `驳回`
- `审批通过`

这些文案会误导用户，以为这是审批卡而不是任务确认卡。

## 5. 推荐模板字段设计

建议钉钉卡片模板里定义下面这些字段。

### 5.1 基础字段

- `title`
  - 固定：`确认执行 Sonar 自动修复`
- `status`
  - 默认：`待确认`
- `jobId`
- `repository`
- `author`
- `projectKey`
- `baseBranch`
- `triggerUser`

### 5.2 运行参数字段

- `issueKeys`
- `skipIssueKeys`
- `maxIssues`
- `reviewerEmail`
- `notifyUserId`
- `changeSummary`

### 5.3 辅助说明字段

- `footerHint`
  - 建议内容：
    - `请确认本次修复范围和限制条件无误后再执行`
- `fallbackHint`
  - 建议内容：
    - `若卡片点击异常，可发送：确认任务 <job_id> / 取消任务 <job_id>`

## 7. 视觉与交互建议

### 7.1 颜色

建议：

- 标题色：深色正文
- 状态标签：
  - `待确认`：蓝色或橙色
  - `已确认`：绿色
  - `已取消`：灰色
  - `确认无效 / 无权限`：红色

### 7.2 排版

建议：

- `任务编号 / 仓库 / 作者 / 项目 / 基线分支` 用短字段列表
- `issue_keys / skip_issue_keys` 用多行文本块
- `max_issues / 审阅者账号 / 结果通知账号` 用短字段列表
- `changeSummary` 单独成一行，避免和主参数混在一起

### 7.3 交互

建议：

- `确认执行` 用主按钮
- `取消` 用次按钮或危险按钮
- 卡片回调后把状态回写成：
  - `已确认`
  - `已取消`
  - `无权限`
  - `确认无效`

## 8. 与当前项目逻辑的字段映射

当前项目已有的确认卡 payload 字段是：

- `title`
- `fields`
- `actions`

其中 `fields` 里已有这些 label：

- `任务编号`
- `仓库`
- `作者`
- `项目`
- `基线分支`
- `issue_keys`
- `skip_issue_keys`
- `max_issues`
- `审阅者账号`
- `触发人`

建议后续代码适配时改成**明确映射到正式模板字段**，而不是再复用旧的示例审批字段名：

- 不再使用：`type`
- 不再使用：`amount`
- 不再使用：`reason`

推荐新的模板数据构建函数，直接输出第 6 节里的结构。

## 9. 状态回写设计

按钮点击后，卡片状态建议这样更新：

### 9.1 已确认

- `status = 已确认`
- 按钮区可隐藏或禁用
- 底部提示改为：
  - `任务已进入队列，请稍后查看执行结果`

### 9.2 已取消

- `status = 已取消`
- 按钮区可隐藏或禁用
- 底部提示改为：
  - `本次手动修复请求已取消`

### 9.3 无权限

- `status = 无权限`
- 保持原卡片主体内容
- 底部提示改为：
  - `当前用户没有确认或取消该任务的权限`

### 9.4 确认无效

- `status = 确认无效`
- 底部提示改为：
  - `该确认已过期或任务状态已变化，请重新发起修复命令`

## 10. 推荐的后续实现顺序

建议按下面顺序落地：

1. 在钉钉卡片平台创建专用模板
2. 为模板绑定本设计里的字段
3. 申请 `Card.Instance.Write`
4. 将模板 ID 写入 `.env`
5. 调整 [dingtalk_stream_service.py](D:/MyProjects/pi-sonar-agent/src/dingtalk_stream_service.py)
   - 使用正式模板字段
   - 不再使用示例审批字段映射
6. 小范围联调：
   - 发起修复
   - 展示确认卡片
   - 点击确认
   - 队列执行
   - 结果回推

## 11. 当前结论

对于 `pi-sonar-agent`，正式确认卡片应当是：

- **任务确认卡**
- **配置确认卡**
- **可回调卡**

而不是审批卡。

后面只要按这份设计建模板，再把模板 ID 配进项目，我们就能把现在的文本确认平滑升级成真正可点击、语义正确的钉钉确认卡。
