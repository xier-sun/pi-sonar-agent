description: 为认知复杂度过高的修复提供更稳定的最小重构策略和审阅要点。

## Fix
- 在满足统一 `C# 质量门禁` 的前提下执行复杂度收口，不要为了降低复杂度破坏 async、命名、XML 文档、LINQ 语法或中文业务表达。
- 首选在目标方法体内收口：提前返回、条件扁平化、局部变量合并、拆小循环体，不要先做跨文件重构。
- 只有当目标方法内收口明显不够时，才提取 private helper；helper 必须单向服务当前目标方法，不要顺手抽象通用层。
- 提取 helper 后，目标方法应变成更清晰的编排式调用；不要把业务判断条件偷换到 helper 里。
- 不要改公开签名，不要新增 DTO/上下文类型，除非当前 issue 明确必须这么做。
- 完成前重新阅读目标方法和新增 helper，确认复杂度下降来自结构收口，而不是删除业务分支。

## Review
- 先按统一 `C# 质量门禁` 检查当前 patch，再判断复杂度是否实质下降。
- 重点看复杂度下降是否来自目标方法本身，而不是把原有复杂判断原封不动平移到不相关方法。
- 如果新增了 private helper，确认 helper 只承接局部逻辑，没有改变判断顺序、聚合顺序、异常处理或返回结果。
- 如果 patch 触达相邻方法，确认这些改动只是配套收口，不是借机扩散到额外业务逻辑。
- 对 approve 来说，不要求 patch 提供“复杂度计算证明”，但必须能从代码结构上看出分支/嵌套被实质收口。

## Main
- 在没有违反统一 `C# 质量门禁` 的明显 blocker 前提下，再判断复杂度收口是否足够进入编译。
- 只有当 patch 明确改到了目标方法，且 Review 没指出明显逻辑漂移或 helper 滥用时，才进入编译。
- 如果当前 patch 只是搬移代码、没有明显简化目标方法结构，优先 retry。
- 如果新增 helper 但看不出主方法更清晰，或疑似改变业务编排顺序，优先 retry。
